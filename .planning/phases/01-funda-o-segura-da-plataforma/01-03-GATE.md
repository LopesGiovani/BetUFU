## Contrato local detalhado aprovado por linha

### 1. Compose, dependências, volumes e rede

- Toda invocação Compose contém literalmente `docker compose --env-file infra/.env.example -f infra/compose.yaml`; nos blocos que enviam um script POSIX por stdin, essa sequência aparece depois do operador de pipeline.
- Antes da primeira invocação Compose de cada bloco aprovado, o preflight PowerShell 5.1 da seção 3 deve executar no mesmo processo, rejeitar qualquer variável contratual já definida no ambiente e imprimir somente os nomes conflitantes. O ambiente do shell tem precedência sobre `--env-file`; `${VAR:?erro}` garante presença, não origem nem igualdade.
- Toda validação do modelo Compose usa `docker compose --env-file infra/.env.example -f infra/compose.yaml config -q`. Ficam proibidos em evidência registrada `config` sem `-q`, `config --environment`, `env`, `printenv`, `docker inspect`, `set -x`, `curl -v` e `curl --trace*`, pois podem revelar valores resolvidos ou o ambiente do contêiner.
- Cada comando é uma invocação separada. No PowerShell 5.1, os payloads multilinha de SeaweedFS/Keycloak usam *here-string* literal enviado por stdin, nunca um script inline aninhado em `sh -c '...'`. Antes do pipeline, cada payload POSIX troca CRLF por LF e acrescenta uma última linha de comentário `#`; assim, o CRLF que o PowerShell 5.1 adiciona ao fim da entrada nativa fica dentro do comentário, não vira parte de um comando. Verificar `$LASTEXITCODE` imediatamente e parar antes do comando seguinte quando não zero.
- As cinco invocações PostgreSQL começam literalmente por `docker compose --env-file infra/.env.example -f infra/compose.yaml`, como exige o Plano. SQL/scripts são preparados em variável de argumento sem aspas duplas internas, evitando o bug de marshaling legado do PowerShell 5.1 sem relaxar o prefixo.
- `depends_on.condition: service_healthy` é usado apenas para Keycloak depender do PostgreSQL. SMTP não é uma dependência de startup do Keycloak; os demais serviços são independentes.
- O `up` comportamental é `docker compose --env-file infra/.env.example -f infra/compose.yaml up -d --wait`.
- Os quatro volumes aprovados usam chaves e `name:` reais idênticos: `betufu-local-postgres-data`, `betufu-local-redis-data`, `betufu-local-seaweed-data` e `betufu-local-mailpit-data`.
- PostgreSQL 18 monta o volume em `/var/lib/postgresql`, conforme o layout da imagem 18; Redis monta em `/data`; SeaweedFS em `/data`; Mailpit usa `/data/mailpit.db`.
- Redis executa AOF e `requirepass`; o serviço injeta `REDISCLI_AUTH: ${BETUFU_REDIS_PASSWORD:?BETUFU_REDIS_PASSWORD obrigatória}`, usa `command: ["redis-server", "--appendonly", "yes", "--requirepass", "${BETUFU_REDIS_PASSWORD:?BETUFU_REDIS_PASSWORD obrigatória}"]` e o healthcheck `redis-cli -e ping`. Mailpit define `MP_DATABASE=/data/mailpit.db`, `MP_DISABLE_VERSION_CHECK=true` e `MP_BLOCK_REMOTE_CSS_AND_FONTS=true`.
- `stop/start` e `down` sem opção de volumes preservam os quatro volumes. `down -v`, `down --volumes`, `docker volume rm` e prune capaz de removê-los são resets locais destrutivos e exigem bloco e aprovação separados.
- Não declarar `container_name`, não usar rede do host e não publicar uma porta sem bind `127.0.0.1`.

- `2.1.1` é o primeiro release oficial com `docker compose up --wait`;
- a documentação atual confirma que `--wait` espera `running|healthy` e implica modo detached;
- a documentação oficial confirma `depends_on.condition: service_healthy`;
- Compose Python V1 não atende ao contrato;
- a versão `5.3.1` observada atende ao piso, mas a execução nativa em Linux ainda não foi realizada porque o Compose planejado não existe e nenhum contêiner está autorizado antes do Gate.
- antes do primeiro `config -q` ou `up`, executar `docker compose --env-file infra/.env.example -f infra/compose.yaml version --short`, exigir código zero e versão semântica `>= 2.1.1`; falha ou versão inferior interrompe o bloco sem fallback para Compose Python V1.

| `BETUFU_OIDC_ISSUER_URI` | `http://localhost:8081/realms/betufu-local` | issuer consumido pelo Spring no host |
| `BETUFU_TECHNICAL_USERNAME` | `technical` | conta técnica somente local |
| `BETUFU_TECHNICAL_PASSWORD` | `betufu-local-technical` | senha local da conta técnica |
| `BETUFU_TECHNICAL_EMAIL` | `technical@betufu.local` | destinatário de prova no Mailpit |
| `BETUFU_S3_ENDPOINT` | `http://127.0.0.1:8333` | endpoint genérico S3 para o backend no host |
| `BETUFU_S3_BUCKET` | `betufu-local` | bucket privado local |
| `BETUFU_S3_REGION` | `us-east-1` | região de assinatura S3 |
| `BETUFU_S3_ACCESS_KEY_ID` | `betufu-local-s3-access` | credencial local mapeada ao SeaweedFS |
| `BETUFU_S3_SECRET_ACCESS_KEY` | `betufu-local-s3-secret` | credencial local mapeada ao SeaweedFS |
| `BETUFU_S3_FORCE_PATH_STYLE` | `true` | compatibilidade do endpoint local |

O contrato S3 contém exatamente essas seis variáveis. O esquema de `BETUFU_S3_ENDPOINT` é a única fonte para HTTP/HTTPS; `BETUFU_S3_TLS_ENABLED` não deve ser declarado. O endpoint aprovado atende ao backend executado no host/IDE; o futuro perfil completo em contêiner deve sobrescrever somente o valor do endpoint para `http://seaweedfs:8333`, sem alterar nomes, selecionar provedor de produção ou acoplar o backend ao SeaweedFS. O Compose mapeia explicitamente `BETUFU_S3_REGION -> AWS_REGION`, `BETUFU_S3_ACCESS_KEY_ID -> AWS_ACCESS_KEY_ID`, `BETUFU_S3_SECRET_ACCESS_KEY -> AWS_SECRET_ACCESS_KEY` e `BETUFU_S3_BUCKET -> S3_BUCKET` somente dentro do serviço SeaweedFS. O backend nunca recebe nomes específicos do provedor local.

### 4. SeaweedFS local e provas S3

Topologia aprovada:

```yaml
command: ["mini", "-dir=/data", "-master.telemetry=false"]
environment:
  AWS_REGION: ${BETUFU_S3_REGION:?BETUFU_S3_REGION obrigatória}
  AWS_ACCESS_KEY_ID: ${BETUFU_S3_ACCESS_KEY_ID:?BETUFU_S3_ACCESS_KEY_ID obrigatória}
  AWS_SECRET_ACCESS_KEY: ${BETUFU_S3_SECRET_ACCESS_KEY:?BETUFU_S3_SECRET_ACCESS_KEY obrigatória}
  S3_BUCKET: ${BETUFU_S3_BUCKET:?BETUFU_S3_BUCKET obrigatório}
ports:
  - "127.0.0.1:8333:8333"
volumes:
  - betufu-local-seaweed-data:/data
```

Definição obrigatória no bloco superior de volumes do Compose:

```yaml
volumes:
  betufu-local-seaweed-data:
    name: betufu-local-seaweed-data
```

O `weed mini` é o modo all-in-one oficial; a imagem já possui entrypoint que transforma `mini` em `/usr/bin/weed mini`, volume `/data`, `curl` e bucket bootstrap por `S3_BUCKET`. Ele é adotado somente para desenvolvimento local, sem alta disponibilidade, redundância ou garantia de backup, e não representa escolha de armazenamento para homologação/produção. `-master.telemetry=false` desativa explicitamente a telemetria do master, evitando chamadas de saída do serviço local. No SeaweedFS 4.41, `AWS_ACCESS_KEY_ID` e `AWS_SECRET_ACCESS_KEY` criam uma identidade estática com conta e ação administrativas; esse privilégio amplo foi aceito somente para o serviço local em loopback, e “bucket privado” significa rejeitar acesso anônimo, não aplicar privilégio mínimo por bucket. Omitir qualquer chave faz o loader ignorar essa identidade e, sem outra configuração, ativa `Allow All`, por isso a interpolação obrigatória e o teste 403 são controles de segurança. Falha ao assegurar o bucket é somente warning no processo `mini`; `/readyz` retorna 200 sem validar filer, bucket ou autenticação e serve apenas como sinal do processo/gateway. A autoridade funcional é a sequência PUT/GET/403 e GET pós-restart aprovada abaixo. Fontes: [README oficial 4.41](https://github.com/seaweedfs/seaweedfs/blob/4.41/README.md), [credencial administrativa por ambiente](https://github.com/seaweedfs/seaweedfs/blob/4.41/weed/s3api/auth_credentials.go), [bootstrap de bucket](https://github.com/seaweedfs/seaweedfs/blob/4.41/weed/command/mini.go), [handler oficial de `/readyz`](https://github.com/seaweedfs/seaweedfs/blob/4.41/weed/s3api/s3api_status_handlers.go) e [implementação oficial da telemetria do master](https://github.com/seaweedfs/seaweedfs/blob/4.41/weed/command/master.go).

O Dockerfile exato de 4.41 usa Alpine no estágio final, executa `apk upgrade` e instala `curl`; Alpine fornece `sh`, `rm`, `grep` e `cmp` por BusyBox. As opções exigidas não são recentes: `--retry-all-errors` existe desde curl 7.71.0, `--aws-sigv4` desde 7.75.0 e `--fail-with-body` desde 7.76.0. Como a política deste Gate proíbe executar a imagem antes da aprovação, o primeiro smoke autorizado deve confirmar os binários e opções dentro do digest aprovado e bloquear todas as provas seguintes se houver divergência. Fontes: [Dockerfile oficial 4.41](https://github.com/seaweedfs/seaweedfs/blob/4.41/docker/Dockerfile.go_build) e [manual oficial do curl](https://curl.se/docs/manpage.html).

### 5. Realm, cliente, redirects e papel técnico

Import aprovado:

- Keycloak executa `start-dev --import-realm` somente no ambiente local;
- `infra/keycloak/realm-betufu.json` é montado read-only como `/opt/keycloak/data/import/betufu-local-realm.json` para respeitar a convenção de import;
- `${BETUFU_OIDC_CLIENT_SECRET}` e `${BETUFU_TECHNICAL_PASSWORD}` permanecem placeholders no JSON versionado;
- o import de startup ignora um realm já existente. Mudança de JSON ou de placeholder depois da primeira inicialização não reconcilia o realm; reset/reimport destrutivo exige bloco e aprovação próprios;
- admin bootstrap usa somente `KC_BOOTSTRAP_ADMIN_USERNAME` e `KC_BOOTSTRAP_ADMIN_PASSWORD`;
- `KC_HEALTH_ENABLED=true` e `KC_METRICS_ENABLED=true`; a gestão 9000 não é publicada.
- o realm `betufu-local` declara `enabled: true`, `registrationAllowed: false`, `resetPasswordAllowed: true` e `verifyEmail: false`; a recuperação nativa permanece disponível, enquanto a prova SMTP dispara manualmente `send-verify-email` sem impor verificação global a cada login;
- o tema de login do realm é `betufu`; não é criado tema de e-mail nesta fase.

Mapeamento exato aprovado dentro do serviço Keycloak; nenhum destes valores é injetado apenas por efeito de `--env-file`:

```yaml

  KC_DB: postgres

  KC_DB_USERNAME: ${KEYCLOAK_DB_USER:?KEYCLOAK_DB_USER obrigatória}
  KC_DB_PASSWORD: ${KEYCLOAK_DB_PASSWORD:?KEYCLOAK_DB_PASSWORD obrigatória}
  KC_BOOTSTRAP_ADMIN_USERNAME: ${KC_BOOTSTRAP_ADMIN_USERNAME:?KC_BOOTSTRAP_ADMIN_USERNAME obrigatório}
```

Realm, client id, username e e-mail técnico permanecem literais determinísticos no JSON; apenas os dois segredos do realm usam placeholders. O Keycloak recebe somente `KEYCLOAK_DB_*` para sua conexão JDBC, nunca `BETUFU_DB_*`.

Fonte: [import/export oficial](https://www.keycloak.org/server/importExport) e [container oficial](https://www.keycloak.org/server/containers).

Cliente confidencial `betufu-bff`:

- `enabled: true`, `protocol: "openid-connect"`, `publicClient: false` e `clientAuthenticatorType: "client-secret"`;
- Authorization Code habilitado por `standardFlowEnabled: true`; implicit flow, Direct Grant, service account e authorization services desabilitados;
- PKCE obrigatório com `S256`;
- redirect URI exatamente `http://localhost:4200/login/oauth2/code/keycloak`;
- post-logout redirect exatamente `http://localhost:4200/`;
- `webOrigins` exatamente `http://localhost:4200`;
- `fullScopeAllowed: false`;
- `defaultClientScopes` é exatamente `["web-origins", "acr", "basic", "profile", "email"]`, preservando os claims OIDC nativos necessários sem incluir o escopo padrão `roles`;
- `optionalClientScopes` é exatamente `[]`;
- `clientScopeMappings` concede ao cliente `betufu-bff` somente o client role `TECHNICAL`, sem escopo para qualquer outro papel;
- nenhum `*`, `+`, prefixo, barra ou porta alternativa;
- o validador Node planejado compara por igualdade e os testes negativos exigem non-zero para cada mutação insegura.

Modelo de autorização aprovado:

- `TECHNICAL` é client role do cliente `betufu-bff`, não realm role;
- a conta técnica tem ID determinístico local `00000000-0000-0000-0000-000000000101`, username `technical`, e-mail `technical@betufu.local`, `enabled: true`, `emailVerified: false`, senha não temporária, `requiredActions: []` e somente `clientRoles: {"betufu-bff":["TECHNICAL"]}`;
- papéis administrativos/de domínio não são criados no Keycloak;
- mapper `oidc-usermodel-client-role-mapper` filtrado explicitamente por `betufu-bff`;
- claim `betufu_roles` é array de strings somente no ID token;
- o Plano 01-26 aceita somente `TECHNICAL` e produz `ROLE_TECHNICAL`; papel inesperado não vira autoridade Spring.

Não criar fluxo MFA customizado, não atribuir `CONFIGURE_TOTP` à conta técnica e não inferir política para futuros usuários administrativos neste Gate. As páginas e capacidades MFA nativas continuam sob responsabilidade do Keycloak; eventual obrigatoriedade de MFA exige decisão própria posterior.

Prova reexecutável aprovada:

1. apagar somente a caixa local de desenvolvimento para eliminar falso positivo antigo;

Contrato aprovado do bootstrap e isolamento:

- o script inicia com `#!/bin/sh` e `set -eu`; toda chamada `psql` usa `--set ON_ERROR_STOP=1`;
- nomes e senhas entram como variáveis `psql`, nunca por concatenação de shell. SQL dinâmico usa `format('%I', identificador)` e `format('%L', literal)` e é executado por `\gexec`;
- `CREATE DATABASE` não fica dentro de `DO` nem de transação: uma consulta `SELECT format(...) WHERE NOT EXISTS (...) \gexec` faz a criação idempotente; roles usam a mesma técnica, seguida de `ALTER ROLE` determinístico para flags e senha;
- `PUBLIC` perde `CONNECT` e `TEMPORARY` em `betufu_local`, `keycloak_local`, `postgres` e `template1`; `template0` já permanece com `datallowconn=false`;
- cada login recebe acesso somente ao database do qual é owner e não recebe membership em outro papel;
- o script pode ser reexecutado sem duplicar roles/databases e deve ser reexecutado uma vez manualmente durante a prova comportamental;
- ele roda pelo entrypoint dentro do PostgreSQL e nunca no host. O serviço recebe explicitamente `BETUFU_DB_*` e `KEYCLOAK_DB_*`; `--env-file` sozinho não faria essa injeção.

A imagem oficial executa `/docker-entrypoint-initdb.d` somente quando o diretório de dados está vazio. Se o primeiro bootstrap falhar, a inicialização fica bloqueada: reiniciar cegamente não reexecuta o script. Diagnóstico e eventual reset destrutivo do volume `betufu-local-postgres-data` exigem bloco e aprovação separados.

Prova de owners e flags:

```powershell
$postgresContractSql = @'
DO $contract$
BEGIN
  IF (
    SELECT count(*)
    FROM pg_database
    WHERE (datname = 'betufu_local' AND pg_get_userbyid(datdba) = 'betufu_app')
       OR (datname = 'keycloak_local' AND pg_get_userbyid(datdba) = 'keycloak_app')
  ) <> 2 THEN
    RAISE EXCEPTION 'database owner contract mismatch';
  END IF;

  IF (
    SELECT count(*)
    FROM pg_roles
    WHERE rolname IN ('betufu_app', 'keycloak_app')
      AND rolcanlogin
      AND NOT rolsuper
      AND NOT rolcreatedb
      AND NOT rolcreaterole
      AND NOT rolreplication
      AND NOT rolbypassrls
  ) <> 2 THEN
    RAISE EXCEPTION 'database role flags contract mismatch';
  END IF;

  IF EXISTS (
    SELECT 1
    FROM pg_auth_members membership
    JOIN pg_roles member_role ON member_role.oid = membership.member
    WHERE member_role.rolname IN ('betufu_app', 'keycloak_app')
  ) THEN
    RAISE EXCEPTION 'unexpected database role membership detected';
  END IF;

  IF NOT (
    has_database_privilege('betufu_app', 'betufu_local', 'CREATE')
    AND has_database_privilege('betufu_app', 'betufu_local', 'CONNECT')
    AND has_database_privilege('betufu_app', 'betufu_local', 'TEMPORARY')
    AND has_database_privilege('keycloak_app', 'keycloak_local', 'CREATE')
    AND has_database_privilege('keycloak_app', 'keycloak_local', 'CONNECT')
    AND has_database_privilege('keycloak_app', 'keycloak_local', 'TEMPORARY')
  ) THEN
    RAISE EXCEPTION 'owner database privilege contract mismatch';
  END IF;

  IF EXISTS (
    SELECT 1
    FROM (
      VALUES
        ('betufu_app', 'betufu_local'),
        ('keycloak_app', 'keycloak_local')
    ) AS expected(role_name, database_name)
    CROSS JOIN pg_database database_under_test
    WHERE database_under_test.datallowconn
      AND has_database_privilege(expected.role_name, database_under_test.datname, 'CONNECT')
          IS DISTINCT FROM (database_under_test.datname = expected.database_name)
  ) THEN
    RAISE EXCEPTION 'database CONNECT allowlist mismatch';
  END IF;

  IF EXISTS (
    SELECT 1
    FROM pg_database database_under_test
    CROSS JOIN LATERAL aclexplode(
      COALESCE(database_under_test.datacl, acldefault('d', database_under_test.datdba))
    ) AS database_acl
    WHERE database_under_test.datname IN ('betufu_local', 'keycloak_local', 'postgres', 'template1')
      AND database_acl.grantee = 0
      AND database_acl.privilege_type IN ('CONNECT', 'TEMPORARY')
  ) THEN
    RAISE EXCEPTION 'PUBLIC database privilege detected';
  END IF;
END
$contract$;

SELECT datname, pg_get_userbyid(datdba) AS owner
FROM pg_database
WHERE datname IN ('betufu_local', 'keycloak_local')
ORDER BY datname;

SELECT rolname, rolcanlogin, rolsuper, rolcreatedb, rolcreaterole, rolreplication, rolbypassrls
FROM pg_roles
WHERE rolname IN ('betufu_app', 'keycloak_app')
ORDER BY rolname;
'@
$postgresContractSql = ($postgresContractSql -replace '\s+', ' ').Trim()
docker compose --env-file infra/.env.example -f infra/compose.yaml exec -T postgres psql --username postgres --dbname postgres --set ON_ERROR_STOP=1 --command $postgresContractSql
if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }
```
