### Substituição de segurança da Matriz A

A resolução autorizada da Matriz A produziu um lockfile estruturalmente válido, porém `npm audit --audit-level=high` retornou código `1` por `GHSA-5xrq-8626-4rwp`/`CVE-2026-47429`: `vitest@4.0.8` pertence à faixa crítica `>=4.0.0 <4.1.0`. Nenhum `npm audit fix` foi executado e esse lockfile permanece rejeitado.

LopesGiovani aprovou a Matriz B no instante registrado no frontmatter. Ela preserva as outras 13 dependências diretas e substitui somente `vitest@4.0.8` por `vitest@4.1.10`. Na data da auditoria (`2026-08-11`), a versão escolhida era a estável mais recente da linha 4.1, possuía assinatura npm e proveniência SLSA, satisfazia o peer `vitest: ^4.0.8` de `@angular/build@22.1.2` e aceitava o `vite@8.1.5` usado pelo builder. ## Contrato de auditoria do lockfile aprovado

O lockfile aprovado foi resolvido, com autorização própria, sem instalar pacotes nem executar scripts:

```powershell
$npmExitCode = 1
Push-Location -LiteralPath frontend
try {
  npm install --package-lock-only --ignore-scripts
  $npmExitCode = $LASTEXITCODE
}
finally {
  Pop-Location
}
if ($npmExitCode -ne 0) { exit $npmExitCode }
```

O diretório de trabalho explícito é obrigatório no Windows: apesar do contrato documentado de `--prefix`, as formas `npm --prefix frontend install ...` e `npm install --prefix frontend ...` falharam com npm `10.9.8` procurando o `package.json` na raiz. `Push-Location`/`Pop-Location` é compatível com Windows PowerShell 5.1, restaura o diretório mesmo diante de falha e preserva o código de saída. Referências: `https://docs.npmjs.com/cli/v10/using-npm/config/` e `https://github.com/npm/cli/issues/1290`.

A auditoria que sustentou a aprovação global comprovou:

1. `package.json` contém exatamente as 14 versões diretas aprovadas, sem faixas;
