O wrapper e o motor não são a mesma versão nem o mesmo artefato. O wrapper **não valida o hash do JAR**. Portanto:

- todo comando npm usa `--ignore-scripts`; o lifecycle publicado nunca é executado;
- `generate:api` e `generate:api:check` não podem permitir download automático nem invocar um version manager do wrapper;
- o runner chama somente o JAR já adquirido e verificado, por caminho aprovado;
- geração/check normais falham se o JAR estiver ausente, tiver tamanho divergente ou SHA-256 divergente;
- o hash do JAR é conferido antes e depois de cada geração/check.

### Fronteira de confiança temporária do Java local

Na estação local, o runner resolve o executável pelo comando `java` disponível no `PATH`; ele não fixa hoje o caminho nem o hash de uma distribuição JDK. Antes de executar o JAR, o runner exige as propriedades exatas `java.specification.version=25`, `java.version=25.0.4` e `java.vendor=Eclipse Adoptium`. LopesGiovani aceita temporariamente essa fronteira para desenvolvimento local: a checagem reduz drift acidental de versão/fornecedor, mas não prova a identidade binária do executável encontrado no `PATH`.

Fixar uma distribuição JDK, sua origem e sua identidade imutável pertence à futura decisão de CI e não pode ser inferido deste aceite local. Alteração de runtime, vendor ou forma de resolução reabre o Gate; esta decisão não autoriza download, instalação ou substituição de Java.

## Achado de revisão da Task 3 e correção aprovada

A revisão da Task 3 identificou um bloqueio antes do Checkpoint I: com `servers: [{ url: / }]`, o OpenAPI Generator 7.24.0 materializa em `api.base.service.ts` o fallback `protected basePath = 'http://localhost';`. O `provideApi('')` do host atual sobrescreve esse valor durante a inicialização normal, mas o fallback absoluto permanece inseguro como comportamento de reserva: uma instanciação sem esse provider pode sair da origem atual e deixar de receber o XSRF nativo do Angular.

A árvore em `frontend/src/app/api/generated/` continua machine-owned e não pode ser corrigida manualmente. A correção durável aprovada pertence ao runner e obedece ao seguinte contrato fail-closed:

1. depois da geração temporária e antes de qualquer publicação, inspecionar somente `api.base.service.ts`;
2. exigir exatamente uma declaração canônica `protected basePath = 'http://localhost';`;
3. materializar essa única declaração como `protected basePath = '';` tanto em `generate` quanto em `check`;
4. diante de declaração ausente, duplicada ou divergente, falhar antes da publicação e preservar a última árvore válida;
5. não reescrever qualquer outro arquivo, literal ou URL como parte dessa materialização.

Esse bloco reabriu exclusivamente `frontend/scripts/generate-api.mjs` e `frontend/scripts/generate-api.test.mjs` da Task 1, ambos já pertencentes aos 12 paths autorizados. `.gitattributes`, `backend/openapi/betufu.yaml` e `frontend/openapitools.json` permaneceram congelados. Na Task 3, a prova contratual cobre a instanciação sem `provideApi('')`, demonstrando que o fallback vazio ainda produz URL relativa; o validador rejeita qualquer URL HTTP(S) absoluta ativa na árvore gerada, inclusive no serviço-base.

LopesGiovani autorizou especificamente este bloco corretivo, incluindo RED, Java/JAR local já aprovado, geração, testes focais e build development. Depois da correção e da revisão independente sem achados P0–P2, LopesGiovani autorizou separadamente a prova agregada do Checkpoint I. ## Reabertura final — manifesto e análise fail-closed

A revisão final encontrou três lacunas que exigem correção antes de novo fechamento:

1. o scanner manual de comentários pode interpretar `//` dentro de uma expressão regular válida como comentário e ocultar uma URL absoluta ativa posterior;
2. uma URL absoluta construída por concatenação de literais pode escapar de uma busca limitada a um literal único;
3. aceitar apenas “arquivos TypeScript” e um conjunto mínimo obrigatório permite arquivo ou serviço extra não aprovado na árvore gerada.

A defesa primária é um manifesto byte a byte, calculado pelo mesmo `readTreeManifest` do runner: paths relativos POSIX em ordem `localeCompare(..., 'en')`, seguidos por separadores NUL, tamanho decimal, conteúdo integral e novo separador NUL. O valor `701CCD54E5DD910F5AF2E4FCDAE9492CE89A6DAC3BD25731FB48268A1476A6D6` fica preservado somente como **registro histórico incorreto e não reproduzível**. O digest canônico aprovado é `78E92BB17EBC45E25F86CA3D23C66958BDCD1786983DEFDC2DD1050BE8D13D5F`, confirmado por duas gerações Java/JAR reais idênticas e pela árvore versionável final.

O validador Angular aplica o mesmo contrato à árvore versionável. Arquivo ausente, extra, renomeado, conteúdo divergente ou digest divergente bloqueia e aciona rollback seguro.

Depois da auditoria estática de todas as entradas do lockfile — origem exclusivamente `https://registry.npmjs.org/`, integridade SHA-512 e inventário `hasInstallScript` — executar:

```powershell
$npmLsExitCode = 1
$npmAuditExitCode = $null
$auditStdoutLines = @()
Push-Location -LiteralPath frontend
try {
  npm.cmd ls --all --package-lock-only
  $npmLsExitCode = $LASTEXITCODE
  if ($npmLsExitCode -eq 0) {
    $auditStdoutLines = @(npm.cmd audit --audit-level=high --json)
    $npmAuditExitCode = $LASTEXITCODE
  }
}
finally {
  Pop-Location
}
if ($npmLsExitCode -ne 0) { exit $npmLsExitCode }

$auditJson = $auditStdoutLines -join [Environment]::NewLine
if ([string]::IsNullOrWhiteSpace($auditJson)) { throw 'npm audit não produziu stdout JSON válido.' }
try {
  $auditReport = $auditJson | ConvertFrom-Json -ErrorAction Stop
}
catch {
  throw "stdout de npm audit não é JSON parseável: $($_.Exception.Message)"
}
if ($null -eq $auditReport.metadata) { throw 'JSON de npm audit não contém metadata.' }

Write-Output "NPM_AUDIT_EXIT_CODE=$npmAuditExitCode"
Write-Output 'NPM_AUDIT_JSON_BEGIN'
Write-Output $auditJson
Write-Output 'NPM_AUDIT_JSON_END'
```

Falha de `npm ls` encerra antes do audit. Falha técnica que deixe stdout vazio, JSON inválido ou sem `metadata` bloqueia. Se o JSON for válido, o exit code do audit é evidência para deliberação, não motivo para descartar o relatório antes do Checkpoint C. Parar e apresentar JSON completo + código. Não instalar e não “corrigir” o grafo. Esse protocolo foi aplicado no Checkpoint C; qualquer novo achado `critical`/`high` reabre o Gate e exige nova decisão humana explícita.

### Aquisição explícita do JAR — somente após caminho e JAR aprovados e autorização material separada

O executor deve obter `approved_engine_cache_path` do frontmatter já aprovado, resolver o caminho absoluto e provar que ele fica dentro de `frontend/tmp/`. Se o campo estiver nulo, fora do escopo ou atravessar symlink/reparse point, parar. Então:

```powershell

$expectedHash = '4B83CCC6FD43056C8C631CD0195E5100BD0550912502527BAB09AC76152DAB0C'
$jarUrl = 'https://repo1.maven.org/maven2/org/openapitools/openapi-generator-cli/7.24.0/openapi-generator-cli-7.24.0.jar'
$nonce = [Guid]::NewGuid().ToString('N')
$partialPath = "$approvedJarPath.partial.$nonce"

if (Test-Path -LiteralPath $approvedJarPath) { throw 'Destino do JAR já existe; aquisição não sobrescreve.' }
Invoke-WebRequest -UseBasicParsing -Uri $jarUrl -OutFile $partialPath
if ((Get-Item -LiteralPath $partialPath).Length -ne $expectedLength) { throw 'Tamanho do JAR divergente.' }
if ((Get-FileHash -Algorithm SHA256 -LiteralPath $partialPath).Hash -ne $expectedHash) { throw 'SHA-256 do JAR divergente.' }
[System.IO.File]::Move($partialPath, $approvedJarPath)
if ((Get-Item -LiteralPath $approvedJarPath).Length -ne $expectedLength) { throw 'Tamanho pós-rename divergente.' }
if ((Get-FileHash -Algorithm SHA256 -LiteralPath $approvedJarPath).Hash -ne $expectedHash) { throw 'SHA-256 pós-rename divergente.' }
```

`$approvedJarPath` só pode ser definido a partir do caminho exato aprovado no Gate; não há default implícito.
