## Essencial para entender agora

- **Datasource** é a configuração usada pelo Spring para abrir conexões com o banco. O PostgreSQL do Compose já existe, mas o backend iniciado pela IDE ainda precisa receber URL JDBC, usuário e senha.
- **XSRF/CSRF** impede que outro site use silenciosamente a sessão já aberta no navegador. O Spring entrega um valor em cookie legível pelo Angular; em mutações, o Angular devolve o mesmo valor em um header.
- **Tombstone de cookie** é uma instrução de exclusão enviada por `Set-Cookie`: no callback OAuth2, o Spring apaga A e cria B na mesma resposta. O liveness posterior só verifica que B permaneceu; ele não cria B nem prova autenticação por ser público.
- **Double-submit cookie** significa comparar dois locais — cookie e header. Isso prova que o código same-origin conseguiu ler o cookie; não significa que o token esteja criptograficamente ligado à sessão no servidor.
- **Sessão em memória no dev** é uma ponte temporária: permite provar login/XSRF antes da política Redis. Ela perde sessões ao reiniciar o backend e deve ser removida pelo 01-06.

## Por que não criar `GET /api/v1/session/csrf`

Na baseline Spring Security 7.1, `csrf.spa()` configura o repository de cookie e um handler SPA que força o carregamento do token em cada request. Assim, uma resposta segura consegue materializar o cookie sem um endpoint de negócio adicional. Evitar o endpoint neste plano traz três vantagens:

1. não reabre `backend/openapi/betufu.yaml` nem o pipeline gerado do 01-20;
2. não cria uma API que depois precisaria ser tratada como atividade de sessão;
3. mantém a fronteira mínima antes do tracer do 01-21.

O 01-08 deve conservar somente as decisões posteriores de STOMP/origem que ainda fizerem sentido e não pode reintroduzir `CsrfTokenController` ou `CsrfCookieFilter` como duplicação silenciosa.

## Atributos e comportamento que precisam de prova

| Cenário | Resultado obrigatório |
|---|---|
| primeiro request safe / cookie A | um header `Set-Cookie` materializa `XSRF-TOKEN=<cookie-octet não vazio>` com conjunto exato `Path=/`, `SameSite=Lax`, host-only e `HttpOnly=false` (atributo `HttpOnly` ausente); espaço, controle, aspas, vírgula, ponto e vírgula ou barra invertida no valor são rejeitados; sem `Domain`, `Max-Age`, `Expires` ou `Partitioned`; no HTTP loopback, sem `Secure` |
| request HTTP local direto/confiável | cookie não força Secure e continua utilizável no loopback aprovado |
| request HTTPS reconstruído por proxy confiável | cookie recebe Secure; header forwarded de origem não confiável não pode promover o request |
| origem pública reconstruída para OAuth2 | o proxy fixa host e porta separados (`localhost:4200` e `X-Forwarded-Port: 4200`); o callback anunciado ao Keycloak deve ser exatamente `http://localhost:4200/login/oauth2/code/keycloak` |
| cookies `Secure` no login local | o harness transporta cookies `Secure` em HTTP somente nas origens exatas `http://localhost:4200` e `http://localhost:8081`, reproduzindo a exceção de contexto confiável de `localhost`; continua bloqueando outra porta, IP, host, path e qualquer vazamento aplicação↔Keycloak |
| cookie geral quoted do Keycloak | aceita somente um par externo completo de `DQUOTE`, remove esse par antes de montar o header `Cookie` e exige conteúdo interno integralmente válido como `cookie-octet`; aspas incompletas/internas, espaço, barra invertida e controles reprovam como `RUNTIME_COOKIE`; essa normalização não se aplica ao `XSRF-TOKEN`, que continua não quoted |
| transições OAuth2 | aceita somente cliente authorization → Keycloak authorization → formulário hospedado → callback cliente → raiz exata, com método/body/status próprios de cada salto; callback de sucesso exige um único `code`, um único `state` e nenhum `error`, `error_description` ou `error_uri`; `/login?error` exato é falha terminal `RUNTIME_LOGIN`, nunca destino de sucesso |
| PUT autenticado sem cookie | 403 |
| PUT autenticado com cookie e sem header | 403 |
| PUT autenticado com cookie/header diferentes | 403 |
| PUT autenticado com cookie/header iguais | alcança o endpoint e retorna a resposta prevista |
| callback OAuth2 / rotação A→B | exatamente um callback 302 para `/` emite, na ordem original, o tombstone `XSRF-TOKEN=; Expires=Thu, 01 Jan 1970 00:00:10 GMT; Path=/; SameSite=Lax` sem `Max-Age`, seguido de um único B ativo diferente de A; outros cookies podem estar intercalados, mas não outra mutação XSRF |
| liveness após callback | retorna 200, emite zero `Set-Cookie` XSRF e preserva exatamente B no jar; por ser `permitAll`, comprova continuidade do cookie, não autenticação |
| PUTs protegidos com cookie B | header A + cookie B falha e B+B funciona duas vezes com UUID convergente; os PUTs, e não o liveness, comprovam a sessão autenticada; não alegar revogação servidor-side do par antigo A+A |
| redirects sem credencial | cada destino é validado por scheme/host/porta/path exatos, sem userinfo/fragmento; somente origens loopback e issuer aprovados; `code`/`state` só entram no callback OAuth2 exato |
| POST com usuário/senha | action permanece no origin/path hospedado exato do Keycloak; somente 301/302/303/307/308 são reconhecidos, 307/308 são rejeitados para o POST, e body, `Authorization` ou cookie sensível nunca são reenviados a outra origem |
| inspeção HTTP browser-facing | nenhum access token, refresh token, ID token, `Authorization` em HTML/JSON ou a senha técnica conhecida aparece em URL/`Location`, body HTTP ou cookie, incluindo nome percent-encoded, body form-urlencoded e `Set-Cookie` transitório; a checagem acontece antes de armazenar cookie ou seguir redirect, e erro assíncrono rejeita a operação para que o cleanup rode; readiness repete somente falha de transporte; `XSRF-TOKEN` é o valor anti-CSRF intencionalmente legível, não uma credencial de login |
| falha do runner | stderr não é ecoado livremente; somente uma linha de até 600 caracteres que case integralmente com o prefixo fixo, uma regra `RUNTIME_[A-Z0-9_]{1,64}` e mensagem allowlisted de até 512 caracteres pode aparecer como marcador no erro agregado; formato ausente, multiline, com controle ou divergente vira `runtime=absent` |
| DOM e Web Storage | não inspecionados pelo runner HTTP 01-29; a evidência de DOM, `localStorage` e `sessionStorage` pertence obrigatoriamente ao Playwright do Plano 01-21 |

O `CsrfSpaIT` pode construir requests como um navegador para testar atributos do cookie, `request.isSecure()`, rejeições 403, aceitação 204 e pares double-submit independentes; isso não autoriza código Angular a fabricar token nem prova Tomcat/`RemoteIpValve` ou rotação OAuth2. Um teste Node puro prova a allowlist de headers do proxy sem abrir socket. A prova final de confiança do proxy e transição A→B usa o runtime real e login Authorization Code hospedado no Keycloak, não Direct Grant. Para o callback HTTP local, o runner sobrescreve `SERVER_SERVLET_SESSION_COOKIE_SECURE=false` somente no processo dev e particiona seu cookie jar por origem, impedindo vazamento entre `localhost:4200` e `localhost:8081`. O transporte de cookies `Secure` em HTTP é uma exceção exclusiva dessas duas origens `localhost` aprovadas, coerente com o contexto confiável adotado pelo Keycloak; não libera HTTP genérico nem remove o atributo armazenado. Essa proteção do harness continua mais restritiva que cookies de navegador e não substitui a prova Playwright 01-21. Mesmo no runtime, o runner 01-29 observa apenas tráfego HTTP; qualquer afirmação sobre DOM/storage sem o Playwright 01-21 seria falsa.

Em seguida, aplicar literalmente o wrapper `System.Diagnostics.Process` e o bloco `try/finally` normativos da seção **Checkpoint F** do `01-29-PLAN.md`. Esse wrapper usa argumentos separados, `UseShellExecute=false`, leitura incremental assíncrona de stdout/stderr limitada a 2 MiB por stream, stdin assíncrono limitado a 64 KiB e timeout com encerramento confirmado para **cada** `compose version`, `config -q`, `ps --all --quiet`, `image inspect --format '{{.Id}}'`, inspect restrito, `container start`, runner, `container exec` e `container stop`. Nenhum comando externo nu pode substituir o wrapper; inspect completo de imagem ou container permanece proibido. Se o runner sair diferente de zero, somente uma linha de stderr que passe integralmente pela allowlist documentada pode virar o marcador `runtime=RUNTIME_*: ...`; qualquer outro stderr permanece oculto como `runtime=absent`.

Antes de mutar, os dois serviços precisam ter container já existente, estado `running|exited`, ID congelado e `Config.Image` igual à referência aprovada. Ausência aborta, pois o escopo não autoriza criar nem remover container. O único `docker container inspect` permitido usa `--format '{{.Id}}|{{.State.Status}}|{{.State.StartedAt}}|{{.Config.Image}}|{{if .State.Health}}{{.State.Health.Status}}{{else}}none{{end}}'`; inspect completo continua proibido. Estado/ID/StartedAt/imagem/health são relidos sob lock imediatamente antes e depois de cada operação, e ninguém pode operar o projeto Docker em paralelo.

Somente serviços inicialmente `exited` recebem `docker container start <ID-exato>`. O executor faz polling restrito do mesmo ID e fingerprint por até 600 segundos: PostgreSQL precisa ficar `healthy` antes de qualquer start do Keycloak, e depois o Keycloak também precisa ficar `healthy`. O runner recebe obrigatoriamente `--expected-jar-sha256 15D7514BF98EE415D0FC83E6008AE0838ACBD01EE17CB53B09B3ABF33A5A0878 --expected-jar-size 78665537`, recusa divergência antes de Java, cria a sentinela `127.0.0.1:6379`, repete a identidade do JAR no fim e emite exatamente uma linha JSON sanitizada com `identityUuid` e metadata PID/nonce/porta/instante.

O executor passa o UUID validado à consulta por stdin LF usando a única exceção de shell aninhado: `docker container exec -i <ID-PostgreSQL-congelado> sh -e` com script fixo. Dentro do container, primeiro remove `PGHOST`, `PGPORT`, `PGSERVICE`, `PGSERVICEFILE`, `PGOPTIONS` e `PGPASSWORD`; depois `psql` fixa `--host /var/run/postgresql --port 5432`, `--username "$BETUFU_DB_USER"`, `--dbname "$BETUFU_DB_NAME"`, `--no-password`, `ON_ERROR_STOP`, modo quiet/tuples-only/no-align e `statement_timeout=15s`. Stderr deve ser vazio e nenhum segredo entra no argv ou na saída. A sentinela exata `BETUFU_RUNTIME_SQL_OK` confirma PostgreSQL 18, `betufu_local`, `betufu_app`, Flyway V1 bem-sucedida e uma linha do UUID.

O protocolo mantém lock local exclusivo e exige janela humana sem operação Docker paralela; revalida o fingerprint imediatamente dentro do `try`, inicia cada container inicialmente `exited` pelo ID exato e acompanha health pelo mesmo ID. O `finally` roda em sucesso ou falha, percorre em ordem inversa apenas esses serviços, exige mesmo ID/imagem e StartedAt atribuível à tentativa antes de `docker container stop`, compara também o fingerprint final dos serviços `exited` e libera somente o lock criado pelo bloco. Serviço inicialmente `running` nunca é parado; container, rede e volume nunca são removidos. Marcadores sanitizados distintos preservam a existência da falha primária e os alvos de cleanup, e qualquer divergência impede `PASS`. Somente depois do cleanup comprovado o executor emite uma linha JSON agregada e sanitizada com códigos de saída, evidência runtime, sentinela SQL e snapshots inicial/final.

`docker image inspect` é somente local. Se a referência não existir, parar e pedir autorização específica para pull; não substituir tag/digest. O runtime não executa inspect completo, `config` sem `-q`, `env`, `printenv`, `set -x`, `curl -v` ou qualquer comando que exponha valores. O runner aplica deadline global, timeout por etapa e cleanup idempotente em `SIGINT`/`SIGTERM`; timeout ou cleanup incompleto reprovam. DOM e Web Storage continuam fora desta prova HTTP e pertencem ao Playwright do 01-21.
